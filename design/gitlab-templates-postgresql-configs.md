# GitLab 稳定模板 + PostgreSQL 用户配置

2026-09-14。用户提出将个人配置存入 PostgreSQL，公共基础配置继续存于 GitLab。本方案是当前讨论中的推荐架构，供用户审阅；未实现、迁移数据或连接 GitLab/集群。前面的全 Git 和个人分支方案作为对照，配置存储模型确定后再统一实施契约。

## 存放边界

| 数据 | 保存位置与职责 |
| --- | --- |
| 公共 Redis/PostgreSQL 等部署包 | GitLab：manifest、Kustomize base、参数 schema、通用默认值、软件目录和来源说明 |
| 稳定模板与模板更新 | main 保存已审查的模板；更新分支经 CI/MR 合并；版本目录和完整 SHA 固定模板内容 |
| 个人部署默认值、草稿、实例参数 | PostgreSQL，按用户/空间授权读取与修改 |
| 配置修改历史 | PostgreSQL 的不可变配置修订，记录参数快照及模板来源 |
| 环境映射、端口预留、发布任务和实际状态 | PostgreSQL，按现有部署阶段实现 |
| 已确认发布的生成清单 | 第一版的小型非敏感产物持久存于 PostgreSQL，绑定发布修订与摘要；规模扩大后可换成不可变产物存储 |
| 密码、GitLab token、模型 key、集群凭据 | 受控凭据存储；个人参数和生成清单使用引用 |

采用本方案后，PostgreSQL 是用户配置正文的权威存储。用户保存参数不写 GitLab、不创建个人分支或 MR，也不维护个人实例 index.yaml。模板维护者仍在 GitLab 使用分支与 MR；应用服务读取经过批准的模板。

## 用户看到什么

“可选软件”来自 GitLab 的 catalog 元数据，可以在数据库缓存软件名称、版本、来源 SHA 和检查状态；“我的配置”、搜索、分页、详情和历史直接查询 PostgreSQL。模板索引是可重建缓存，个人配置不是缓存。

用户选择 Redis 模板 v1，填写内存 1Gi、存储 10Gi 和自动外部端口，平台检查后保存个人配置修订。此时尚未接集群也可保存部署意图；页面明确显示 Namespace 和端口待解析。main 中的模板通过审查，并不代表该用户配置已经部署。

个人参数适合使用受 schema 约束的 JSONB；用户/空间归属、配置身份、软件标识、修订序号及常用筛选字段使用明确关系字段，避免把权限判断藏在任意 JSON 中。JSONB 的结构灵活性不能替代 Pydantic/参数 schema 校验。参数页面生成只读 YAML 预览，不要求用户编辑任意 Kubernetes 清单。

## 每次保存固定哪些内容

保存创建新的不可变配置修订，至少绑定：

- 配置身份、所属用户/空间、修订序号和创建者。
- GitLab 项目标识、完整模板 commit SHA、包路径、模板版本和 schema 版本/摘要。
- 展开后的实际参数、凭据引用、软件版本与镜像选择，以及明确的环境选择意图。
- 参数检查结果、内容摘要和审计字段。

个人默认值覆盖允许覆盖的公共默认值，显式实例参数再覆盖个人默认值；归属、允许的 Namespace/端口等平台策略不允许被默认值绕过。保存时固定实际生效参数，之后默认值改变不影响旧修订。结构不完整的编辑可存草稿，正式修订要求通过对应的参数校验；草稿不是可发布版本。

写入时在一个数据库事务中校验 expected_revision、幂等标识和权限，保存新修订并更新当前修订指针，避免旧页面覆盖新配置。GitLab 模板解析/下载不放入长时间数据库事务；先获取并校验确定版本的模板，再完成短事务。恢复历史内容也生成新修订，保留审计和后来其他配置的变化。

## 发布时怎样组合

```text
GitLab：已批准模板，固定完整 SHA
                       +
PostgreSQL：选定的不可变用户配置修订
                       ↓
核实目标环境、解析 Namespace 并预留端口
                       ↓
生成本地 Kustomize overlay，渲染并展示差异
                       ↓
保存确定的发布修订、非敏感清单和摘要
                       ↓
独立 Worker 执行该修订，记录真实验证结果
```

Namespace 是已授权映射/初始化，端口按持久预留规则分配。发布修订要固定解析后的目标、Namespace、端口、镜像 digest、生成器/Kustomize 版本、模板内容摘要及生成清单，不能只保存一句“稍后使用最新配置”。Worker 使用被选定的发布输入，执行前核对版本和摘要；重试不读取 main 最新 HEAD 或用户最新草稿。

公共模板 checkout 与从数据库修订生成的 overlay 可以组装到同一隔离工作目录，overlay 只引用本地受控模板。生成产物持久化后才可创建可执行任务；多文件产物与任务的可用标记应一致。第一版小型产物和任务可由 PG 事务关联，避免只将唯一清单保存在 Worker 临时磁盘。

数据库参数修订、发布修订和最近验证成功修订分别记录。用户继续编辑产生新修订，不影响已经提交的任务。部署失败保留原发布输入；恢复旧配置是新的发布，仍需检查环境和存储兼容性，不等于恢复 Redis 数据。

## 模板更新与读取可靠性

main 发布 v2 后，已有配置仍引用原来的 v1 和完整 SHA。用户选择升级时，读取批准的新模板/schema，检查参数兼容性，生成新配置修订；重新解析环境与生成产物后发布。已发布模板目录保持不可变。

main 用于发现当前可选模板，实际读取使用完整 SHA。GitLab 模板版本需要保留可达引用或已验证的源码包归档；旧 SHA 不可用时明确失败，不能改用最新模板。缓存必须按完整版本和摘要校验；GitLab 故障时已有 PG 配置仍可查询，无法获得可靠模板输入的生成操作显示受阻。

## 查询、权限与数据恢复

配置列表、详情、历史、差异、导出和发布均按数据库中的用户/空间授权；Worker 只访问任务绑定的配置和凭据引用。继续遵守 README 的 create_at/update_at/create_by/update_by 字段及日志约定，日志不复制任意参数正文。

本方案要备份 PostgreSQL 中的个人配置、修订、发布产物和权限/审计关联，并验证恢复。仅恢复 GitLab 模板不能恢复个人配置。可重建的是模板目录缓存；个人配置和发布记录是需要持久保护的业务数据。

## 对当前开发计划的影响

阶段 0A 聚焦 GitLab 公共模板目录、稳定版本与参数契约；阶段 0B 改为“模板读取 + PG 个人配置管理”，先实现应用列表、参数表单、保存读回、权限、版本历史和差异。个人 Git 分支、个人索引及用户配置 MR 不作为该方案的交付前提。

阶段 1–2 继续核实集群和验证 Redis 模板；阶段 3 补实际实例、Namespace/端口预留和发布修订；阶段 4 的 Worker 绑定“模板 Git SHA + PG 发布修订”，替换原先“完整实例配置全部来自某个 Git commit”的约定；阶段 5–6 接入真实发布页面和自然语言入口。

实施前需统一替换旧方案的读写源、修订模型、状态和验收说明，按 README 在 [数据库设计](database.md) 补正式表结构与 SQL，再实现迁移与接口。本次只提供存储和流程设计，不创建业务表。验证需覆盖跨用户拒绝、参数校验、并发/幂等、默认值固定、模板升级、产物一致性和数据库恢复；配置保存验收与真实部署验收分开。
