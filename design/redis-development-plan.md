# Redis 一句话部署开发计划

首次确认日期：2026-09-10；2026-09-13 调整为先建立独立的软件 manifest Git 仓库；2026-09-14 用户要求先审阅 GitLab 配置存取设计，阶段 0 增补 0B 设计草案。本文是当前业务开发计划，适用于 `olixops-agent`、`olixops-agent-web` 及其集群接入协作。后续 AI 继续开发、设计部署接口或评审相关改动时，必须先阅读本文，按阶段依赖逐步实施。

本文规定目标、顺序和验收条件；实时进度以 [后端 todo](../todo.md) 为准，前端记录本仓库实现与联调证据。编码、认证、日志、接口约定继续遵守各仓库 README。用户后续明确调整方向时，同步更新计划与进度。当前仅完成计划落档，新增阶段 0 及原有阶段 1–6 均未验收。

## 当前决定与范围

**最新存储方案讨论（2026-09-14）：** 用户提出个人配置正文存 PostgreSQL、公共稳定模板存 GitLab，推荐设计见 [模板与个人配置分离方案](gitlab-templates-postgresql-configs.md)。目前仍为设计审阅；下方保留此前全 Git 草案。若采用新模型，阶段 0B 调整为 PG 配置管理，阶段 3–4 按“模板 Git SHA + PG 配置/发布修订”实现，不再要求个人分支或将实例正文写回 Git。

- 第一条完整业务链路是：已有 POC Kubernetes 集群内的单实例 Redis，持久存储、认证和通过现有 Gateway 的 TCPRoute 提供访问。
- 当前部署路线采用 Git 配置管理、Kustomize 模板和独立部署 Worker；Worker 使用受控 `kubectl` 调用应用明确的配置版本。Argo CD/Flux 接管执行属于后续可选调整，第一版不同时引入第二个资源执行者。
- 首先建立独立的软件清单 Git 仓库，初版以 `catalog/` 保存版本化软件部署包，以 `instances/` 保存具体实例的非敏感 overlay；目录、版本与职责见 [软件清单仓库设计](software-manifest-repository.md)。实际仓库名称和地址待确定。
- 用户已选择 GitLab 保存配置正文，main 表示稳定配置，更新分支保存修改与草稿；部署默认值同样入 Git。保存、固定 SHA 读取、差异与 MR 流程见 [GitLab 配置管理设计](gitlab-configuration-management.md)，目前为待审阅草案，不代表已授权实施全部接口或已创建 GitLab 资源。稳定配置、环境解析和实际部署分别记录。
- 分支模型补充讨论见 [个人配置分支方案](gitlab-personal-branches.md)：用户提出 main 专注稳定模板、每人长期维护自己的分支。下方 0B 保留原草案流程，实施前按选定模型同步读取源和 MR 目标；当前只完成可行性说明，未建立任何远端分支。
- **Pulumi 暂不使用。** 保留已引入的代码、依赖、诊断与基础自测原样；本计划不增加 Pulumi Provider、业务 Stack 或 state backend，也不把 Pulumi 可用作为 Redis 发布前提。历史 IaC 选型和框架研究中的 Pulumi 路线不是当前实施任务。
- 保留现有 Python/FastAPI、React 和 LangGraph 需求分析。先完成固定参数真实部署，再让自然语言入口调用同一套业务能力。
- Redis 模板基于官方镜像和对应版本配置说明，由项目维护并验证。后续实例创建使用收录的固定模板版本；镜像记录版本与摘要。上游 Redis 配置文件、容器镜像和 Kubernetes 部署清单分别管理。
- PostgreSQL、Redis Sentinel/Cluster、备份恢复、多集群动态管理及 Harness 迁移留待首条业务链路完成后的设计；已有 PostgreSQL 方案分析功能保持。

## 开发起点与职责

已有登录、数据库、日志、持久分析会话和 React 方案页面；`ready` 表示方案就绪，尚未证明目标集群存在或资源已经部署。当前规格还缺少资源配额、存储选择、网关入口等业务字段。既有验证记录见两端 todo，不作为新部署链路的验收结果。

| 位置 | 本计划职责 |
| --- | --- |
| `olixops-k8s-ctl` | 独立 Go/Kubernetes 控制项目；负责 client-go 集群连接、Namespace/存储/工作负载/Gateway 查询及后续受控操作 |
| `olixops-agent` | 参数契约、模板渲染、Git 配置版本、实例与部署任务、Agent 编排 |
| 独立部署 Worker | 使用对应集群凭据，领取持久任务、应用指定版本、核对实际资源和服务 |
| `olixops-agent-web` | 固定参数操作、差异、发布进度、实例详情及自然语言交互 |
| 独立软件清单 Git 仓库 | catalog 中的版本化 manifest/参数契约，以及 instances 中的非敏感 overlay、凭据引用与变更历史 |

集群查询可先调用现有 HTTP 接口并包装为 Agent 工具；MCP 是查询接入方式之一，不要求先重写旧项目。现有 Go 服务的 Helm 写接口不参与这套 Kustomize 资源的发布。

## 阶段 0：建立软件清单仓库与配置管理

### 0A：仓库与 Redis 部署包骨架

**实施：**

1. 确定独立仓库名称、远端地址和分支流程，按软件清单仓库设计划分 catalog、instances、示例和检查目录。
2. 建立 Redis 单实例部署包草案：资源文件划分、参数 schema、软件与模板版本、镜像 digest、Secret 引用和资源归属的元数据契约。
3. 定义实例 overlay 的生成约定和固定 commit 执行规则。平台校验参数后生成实例配置，Worker 消费确定的清单版本。
4. 增加基础目录/参数/引用检查及说明。环境未核实前，只收录草案和非敏感示例；实际模板渲染与集群验证在阶段 2 完成。

**验收：** 仓库及初始提交可定位，Redis 包骨架与参数契约经过检查，能清楚区分通用软件包、示例和真实实例；无明文凭据。仓库存在不代表 Redis 已可发布。远端未确定时先完成独立本地工作，远端发布及阶段验收保持待办。

### 0B：GitLab 配置存取与变更流程（设计待审阅）

按用户要求将配置管理设计前移：绑定私有 GitLab 项目，实现有权限的配置列表、固定 SHA 读取、更新分支、多文件提交、差异与历史；通过 MR 将检查后的候选合入 main。第一版建议由维护者在 GitLab 合并，平台负责同步结果。配置正文、部署默认值和已保存草稿均在 Git；数据库保留授权、Git 索引、操作幂等和流程元数据。

**验收：** 通过真实 GitLab 完成两个用户的授权隔离、保存后读回、版本一致性、并发冲突、错误及回执丢失恢复、MR 合并后定位确定版本，以及从历史创建单配置恢复变更。包含最小配置管理页面联调；阶段 5 仍负责真实资源发布页面。环境未接入时只保存与检查部署意图，不分配实际 Namespace/端口，也不声称可部署。详细范围和待提供条件以设计草案为准。

## 阶段 1：接通集群并确定环境参数

**实施：**

1. 确定 POC 集群标识、查询地址、执行凭据引用、允许使用的 Namespace、StorageClass、镜像来源及 Gateway 控制器/版本。
2. 在 `olixops-k8s-ctl` 中接入 client-go 和受控集群连接。外部调用需要服务鉴权，集群凭据不得返回给调用方；第一版使用明确的固定集群映射。
3. 补充 StatefulSet、PVC、StorageClass、Events、Pod readiness、Gateway/TCPRoute 查询，提供可校验的摘要结果和明确错误。
4. 确定 Gateway 地址、TCP Listener、端口分配与路由关联方式。共享 Gateway/Listener 由平台统一维护；实例拥有自己的 TCPRoute。跨 Namespace 关联按实际控制器和 API 规则校验。

**验收：** 使用真实受限身份查询目标集群，能区分认证失败、目标不存在与连接失败；确认可用存储及 TCPRoute 支持，查询结果不包含 kubeconfig 或密码。未获得集群访问时，完成的客户端与替身测试单独记录，阶段保持待真实验收。

## 阶段 2：完成固定版本 Redis 模板并验证

**实施：**

1. 在阶段 0 的软件清单仓库中完善 Redis Kustomize base 和示例 overlay，包含单实例 StatefulSet、必要 Service、持久卷声明、ConfigMap、Secret 引用及选用外部访问时的 TCPRoute。
2. 定义受支持参数及默认值：实例名、版本、CPU/内存、存储容量与 StorageClass、Namespace、Redis 持久化/认证策略和访问入口。集群事实从阶段 1 获取。
3. 固定上游来源、镜像版本/摘要与模板版本；非敏感配置提交 Git。密码由受控凭据流程提供，Git 保存引用。
4. 先用固定参数验证集群内 Redis，再验证外部 TCP 入口。明确实例资源归属、配置变更生效方式，以及删除实例时 PVC 默认保留的规则。

**验收：** 渲染结果通过结构与目标 API 校验；Redis 通过认证后能 PING 和读写；重建 Pod 后测试数据仍在；从目标客户端网络经 Gateway 实际连接成功。记录测试的模板、镜像、集群和资源身份，并仅清理本次测试资源。Pod Ready、路由被接纳和外部可用分别记录。

## 阶段 3：建立实例、配置修订与 Git 映射

**实施：**

| 对象 | 必须表达的含义 |
| --- | --- |
| 实例 | 持续存在的一套 Redis，具有稳定身份、用户归属、目标集群及资源/存储归属 |
| 配置修订 | 不可变的期望配置，绑定 Git commit、实例路径、模板版本、镜像版本与渲染结果摘要 |
| 部署任务 | 将某个配置修订应用到实例的一次执行，记录尝试、阶段、事件、错误与验证结果 |

完成上述对象的数据库模型、迁移和接口契约；具体命名在实现时遵守 README。沿用已有分析会话关联，区分分析任务与部署任务。

复用阶段 0 的 GitLab 配置读写、变更和修订索引，将经过阶段 2 验证的模板与生成的实例 overlay 固定在可重现的提交中，补齐真实实例、Namespace/端口预留、环境解析与可部署修订的关联。远程配置稳定保存且环境与模板条件满足后才将该修订标记为可发布；Git 发布失败、并发修改或后端回执丢失均须可追踪和核对。用户确认的差异绑定目标与配置内容，修改后重新校验差异。

**验收：** 每个实例都能查到配置来源及部署记录；修改产生新修订；重复请求不会创建第二个实例或重复修订；其他用户不能访问无权限实例。Git 写入失败时不会继续部署未经记录的配置，仓库没有明文凭据。

## 阶段 4：实现固定参数部署 Worker 与恢复

**实施：**

1. 后端持久提交任务，独立 Worker 领取，API 请求不直接等待部署。现有分析消费者持有的数据库长事务不延伸到资源执行。
2. Worker 读取任务绑定的确定 Git commit 和实例路径，核对模板及渲染摘要，完成差异/目标校验后执行受控 `kubectl` 调用。每次执行使用独立目录、明确集群和 Namespace、超时与清理规则。
3. 记录排队、校验、应用、验证、成功或失败阶段；同一实例的写操作跨进程串行，重复提交和重领可核对既有执行。
4. 查询资源并检查 Redis 认证、读写和外部入口；服务状态与部署任务状态分别保存。共享 Gateway 的端口占用须统一分配并防止并发冲突。
5. 保存实例管理的资源清单，明确后续更新中移除资源及删除实例的处理；普通 apply 不能代替完整的删除管理。PVC 按明确保留策略处理。

**恢复契约：** Git 提交与集群应用不是一个事务。分别记录目标修订和最近验证成功修订。Git 成功而部署失败时保留提交，重试仍使用同一修订；执行成功但回执丢失时，先核对资源和服务。部分失败标记实际状态待核对，不能声称仍完整处于上个版本。回退配置是一次新的发布，不等于恢复 Redis 数据。

**验收：** 固定参数接口能完成真实创建和验证；重复提交、同实例并发、Worker 重启、执行成功但回执丢失、路由拒绝及健康检查失败均有可解释状态和恢复路径；重试不创建第二套实例、不偷偷切换到 Git 最新 HEAD。删除验证保留指定数据卷，且不影响共享网关或其他实例。

## 阶段 5：接入前端固定参数发布链路

**实施：** 扩展现有方案页，提供参数编辑、非敏感配置差异、发布入口、轮询进度和失败核对/重试；增加实例详情，展示资源状态、访问地址、配置版本与发布历史。创建完成后接入受支持的资源参数修改及显式删除，展示数据保留规则。同步前后端 schema、错误契约与权限验证。

**验收：** 通过真实后端完成登录、固定参数创建、查看进度、刷新恢复、失败重试、参数修改及删除。页面区分方案就绪、配置已保存、正在部署、验证失败和服务可用；其他用户数据保持隔离。完成仓库 UI 规范要求的桌面/窄屏检查，演示数据不作为实际联调验收。

## 阶段 6：接入现有 LangGraph 自然语言入口

**实施：** 扩展现有规格与模型提取字段，接入真实模型和环境查询。Agent 根据已收录模板理解需求、补齐参数、展示方案，再调用阶段 3–5 的同一套配置与发布接口；模板生成和集群执行由确定的业务实现完成。

**验收：** “在 poc 创建 Redis，内存 512Mi、存储 10Gi，提供外部访问”能完成追问、环境核验、差异确认、Git 记录、部署和实际访问验证。缺参、不支持的配置、查询失败和旧方案修改有明确反馈。自然语言和固定参数入口遵守相同权限、修订绑定与幂等契约；`ready` 仍只表示方案就绪。

## 后续 AI 的推进与交付规则

1. 每次继续业务开发，先读本计划、两端适用规范、相关代码和 todo 阶段记录，确定最早尚未验收的阶段。
2. 按 0 → 1 → 2 → 3 → 4 → 5 → 6 推进，首先建立软件清单仓库和包契约。在当前任务授权范围内，阶段验收通过后继续后续阶段；常规实现和阶段切换无需逐次向用户确认。
3. 外部条件缺失时，在 todo 写明缺少内容、影响阶段、已完成部分与继续条件；继续不依赖该条件的契约设计、模板和测试工作。保留未完成的真实验收项，后续阶段依赖的事实不得用假数据代替。
4. 每个阶段运行适用于改动的检查，补齐能验证实际行为的测试；接口/数据变化同步设计文档和两端解析。分别记录替身测试、真实接口联调、真实集群验证及各自的限制。
5. 按可复核的阶段提交 Git；依据当前任务授权推送。同步 todo 中的变更文件、测试结果、提交与未决项，不把历史测试数量沿用为本轮通过结果。
6. 计划落档不代表开始创建远端仓库或执行集群变更。后续实施使用用户授权的目标与操作范围，先从阶段 0 开始；需要调整目标或顺序时，记录用户最新决定及其影响。
