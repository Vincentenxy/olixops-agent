# GitLab 个人配置分支方案

最新推荐讨论见 [GitLab 稳定模板 + PostgreSQL 用户配置](gitlab-templates-postgresql-configs.md)。若采用 PG 保存个人配置，本文的个人分支和实例索引不再作为交付要求；本文保留供方案比较，目前均未实现。

2026-09-14：用户在审阅配置管理设计时提出“main 稳定模板 + 每个用户自己的长期分支”。本方案说明其可行性与读写规则，供本轮讨论；尚未实现或创建 GitLab 分支。前一版 [配置管理设计](gitlab-configuration-management.md) 使用 main 集中保存所有人的稳定配置，两种分支模型的读取源和 MR 目标不同，实施时需统一采用选定模型。

## 分支职责

| 分支 | 内容与用途 |
| --- | --- |
| `main` | 平台维护的稳定软件模板、参数 schema、通用默认值、非敏感示例和检查规则；不保存真实用户实例配置 |
| `templates/<software>/<change_id>` | 通用模板更新，通过检查和 MR 合入 main |
| `users/<workspace_id>` | 该个人空间选择的模板快照、个人部署默认值和实例配置；长期保存 |
| 可选 `changes/<workspace_id>/<change_id>` | 需要单独审阅的个人变更；从个人分支创建，MR 目标为该个人分支 |

当前一人对应一个个人空间，使用稳定 ID；后续团队空间可沿用相同归属映射。个人配置可以直接通过平台校验并保存到个人分支，无须每次合回 main。要贡献通用模板改进时，由维护者建立只包含模板改动的 MR，不把整条个人分支合入 main。

## 模板与个人配置如何组合

1. 平台选择经过批准的 main 完整提交 A，创建 `users/ws-001`。Git 分支起初指向该提交，因此已有同一份模板快照；没有自动跟随 main 更新的关系。
2. 用户创建 Redis 配置，平台在该分支增加 `workspaces/ws-001/defaults.yaml` 和 `instances/ws-001/<config_id>/config.yaml`，保存为提交 B。配置声明选用 `redis/standalone/v1`，个人参数如内存 1Gi、存储 10Gi。
3. 后端鉴权后将个人分支解析为确定 SHA。以 B 为例，模板、参数 schema、默认值和个人配置都从 B 读取，检查模板内容与批准来源一致；实际使用的默认值展开到实例配置中。
4. 环境未解析时保存配置意图；解析完成后，生成的 overlay 引用该提交内的本地模板，将参数转换为受控 patch。模板快照、参数和生成文件以一个新的配置提交保存，避免从两个浮动分支临时拼接输入。
5. 后续部署绑定个人分支历史中检查通过且用户选定的完整 SHA、配置路径、镜像 digest 和渲染摘要。读取/重试不重新选择当时最新的 main 或个人 HEAD。

```text
main@A
  catalog/redis/standalone/v1/         公共稳定模板

users/ws-001@B
  catalog/redis/standalone/v1/         来自 A 的模板快照
  workspaces/ws-001/defaults.yaml     个人默认值
  instances/ws-001/redis-001/
    config.yaml                      v1 + 内存 1Gi + 存储 10Gi
    overlay/                         环境解析后生成，引用本地 v1

users/ws-002@C
  catalog/redis/standalone/v1/         来自 A 的模板快照
  workspaces/ws-002/defaults.yaml
  instances/ws-002/redis-002/
    config.yaml                      v1 + 内存 512Mi + 存储 5Gi
    overlay/
```

这里的 v1 是模板版本，Redis 软件版本与镜像 digest 单独记录。Git 内部复用未变化的对象，不必因为每个人有一个分支就重新上传一份相同模板；分支在逻辑上仍代表可独立读取的完整快照。

## 如何知道有哪些软件与个人配置

2026-09-14 用户提出 Git 中配置不易发现、读取的问题。GitLab 提供目录与文件 API；平台还需要明确的应用元数据和目录索引，才能将 YAML 文件组织成可浏览的软件列表与个人配置列表。本节为设计补充，索引和接口尚未实现。

| 页面 | 读取来源 | 含义 |
| --- | --- | --- |
| 可选软件 | `main@A` 的 `catalog/index.yaml` | 平台当前收录的软件、模板版本、描述与包路径；能否部署还要看模板/环境验证条件 |
| 我的配置 | `users/<workspace_id>@B` 的 `instances/<workspace_id>/index.yaml` | 当前空间保存的配置 ID、名称、软件、模板版本和正文路径 |
| 配置详情 | 列表返回的 B 中的具体 config.yaml、模板快照和 schema | 使用同一个确定版本还原用户保存的配置 |

示意的个人配置索引如下，展示的是待实现格式，不代表已有这些实例：

```yaml
schema_version: 1
configs:
  - id: redis-001
    name: 测试缓存
    software: redis
    template_version: v1
    path: instances/ws-001/redis-001/config.yaml
```

平台的软件包元数据描述“这是什么软件、版本和参数”，config.yaml 描述“这个用户希望怎样配置”；索引由这些元数据按确定规则生成，不要求用户手工维护。GitLab 的目录枚举用于发现约定的 package.yaml/config.yaml，不能仅凭任意 YAML 文件名推断应用类型。尚未登记或未通过检查的包和实例明确显示待处理，不当作可部署应用。

正常读取流程：后端鉴权并确定个人分支 → 解析为 B → 用文件 API 读取 B 的索引 → 返回本人列表及版本标识 → 点击详情后继续读取 B 的配置正文。可选软件目录独立从 main@A 读取；A 有 v2 而 B 只有 v1 时提示可升级，选择新模板前先完成受控同步，不能把 A 的 schema 直接套在 B 的旧配置上。前端只调用平台 API，不持有 GitLab token，也不需要 clone 仓库。

### 索引一致性与发现遗漏

- 创建、删除、改名或改变索引摘要字段时，配置正文和索引通过一次多文件提交保存。平台先构造候选文件集合再生成索引；CI 验证一致性，不在检查通过后另外补一个修改索引的提交。
- 校验 ID 唯一、索引字段与正文一致、文件存在、路径属于授权空间、无目录穿越或越界链接。索引条目本身不能改变配置归属或授予访问权限。
- 在提交检查和手动“重新同步目录”时，对同一 SHA 的受控目录做完整文件集合核对，发现未登记文件、悬空或重复条目并报错。目录枚举须处理分页；Tree API 按 SHA 的行为在目标 GitLab 版本联调，必要时使用固定 SHA 的受限 Archive 读取。修复索引生成新提交，不能静默忽略遗漏文件或自动部署发现的资源。
- 同一空间的两个请求即使修改不同配置，也可能同时修改索引，因此保存按个人分支协调并校验预期 SHA，复用既有文件前置条件与写后核对规则，禁止最后一次写入覆盖另一条索引记录。
- 索引缺失、格式错误或 GitLab 不可用分别返回明确状态，不显示成“没有配置”。首次个人空间初始化可显式提交空索引，后续空列表才有确定依据。

第一版读取已提交的索引即可，不需要每次打开列表扫描全仓。以后需要大量配置搜索、分页或管理员跨空间统计时，PostgreSQL 可以保存可重建的目录投影：ID、名称、软件、路径、项目、空间、来源 SHA 和同步状态，不保存配置正文。按需刷新是基础，webhook 可以辅助触发同步；旧版本同步结果不能覆盖已确认的新版本索引。配置详情继续按选定 SHA 从 Git 读取，缓存命中也要鉴权。

管理员统计仅遍历平台登记的项目/空间/分支绑定，保留每个空间的同步版本和错误状态，不把任意 Git 分支当作合法用户。可重建的是配置目录和搜索数据；数据库中的用户权限、操作幂等及部署状态仍需独立持久保存。索引设计同时适用于前一版集中 main 的模型，只需统一选定后的配置读取分支。

依据：[GitLab Repository Files API](https://docs.gitlab.com/api/repository_files/)、[Repositories API](https://docs.gitlab.com/api/repositories/)。索引格式、应用登记及数据库投影为平台约定。

## main 发布新模板后如何升级

main 新增 v2 并不会改变 ws-001 正在使用的 v1。平台可提示有可用升级，由用户选择升级的配置；平台从批准的 main 完整提交中同步所需的新模板目录和依赖到个人分支，并记录来源提交、路径和内容摘要。只同步受控模板内容，保留个人参数目录，不执行整仓覆盖。

更新指定实例的模板引用后检查 schema 兼容性，要求补齐新增参数，重新核验环境并生成 overlay。保存新的提交、展示差异，再用于显式发布。个人分支中其他仍选择 v1 的实例继续保留 v1；检查失败不会自动改变已部署版本。发布过的模板目录保持不可变，用户不能自行修改 catalog 或检查代码。

## 保存、检查、审阅和部署分别记录

个人分支 HEAD 表示最新保存。每个配置分别关联最新保存 SHA、检查通过 SHA、选定发布 SHA 和最近验证成功 SHA；一个用户可以在同一分支保存多个配置，但保存其中一个不自动发布其他配置。

初版参数编辑可直接保存并运行检查；如增加 MR 审阅，目标是所属个人分支。个人变更合入个人分支同样应检查确定候选、处理目标前进和并发，不能继续沿用“所有配置 MR 合入 main”的路由。模板 MR 始终合入 main。个人参数保存、模板升级、历史恢复均受权限、幂等与版本冲突检查保护。

保留前一版设计中固定 SHA 读取、多文件提交、操作意图持久化与未知结果恢复的约定；普通保存仍是单父提交，模板同步采用受控文件提交。没有自动合并 main 或对个人分支执行 rebase/force push。恢复某个配置时在个人分支上新增提交，只恢复该对象，避免回退同分支其他实例；已选定发布的历史 SHA 不随新编辑变化。

## 权限及当前适用范围

后端根据登录身份映射允许访问的个人分支和路径。数据库保存身份/空间权限、分支绑定、修订引用、操作摘要和状态；配置正文及草稿仍在 Git，凭据只保存引用。首次创建个人分支必须以模板专用 main 为起点，不能从已含其他用户配置的分支创建。

分支不提供仓库读取保密边界。普通用户通过平台使用，不获得共享 GitLab 项目的 clone 权限；如果客户需要直接访问 GitLab 且要求配置彼此保密，应使用独立私有项目。个人分支适合当前由平台统一管理 GitLab 的内部使用方式；后续用户/配置规模增大时，再评估分支数量、模板同步维护和按组织拆仓。

该方案会把默认读取源从 main 改为所属个人分支，把个人配置 MR 目标改为个人分支，把“模板稳定”与“个人配置检查通过”分别表达。若采用，需要同步配置接口、分支保护、CI、修订索引及阶段 0B 验收；真实 Namespace/端口分配和 Worker 仍按后续阶段实施，当前讨论不代表已接入。

依据：[Git 分支与快照](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell)、[Kustomize base/overlay](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/)、[GitLab 角色与权限](https://docs.gitlab.com/user/permissions/)。模板同步、个人配置状态和分支归属为本平台建议约定。
